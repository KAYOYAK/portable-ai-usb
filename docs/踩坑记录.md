# 把一个 9B 大模型装进 U 盘：踩坑记录

这是 [portable-ai-usb](https://github.com/KAYOYAK/portable-ai-usb) 的开发过程记录。

如果你正在做类似的事（把本地大模型塞进移动介质、在陌生电脑上跑起来），
下面这些坑你大概率会撞上。每一条都写了**报错原文**，方便你搜到这里。

---

## 一、cmd.exe 会把带中文的 `.bat` 解析错位

### 现象

双击运行，菜单没出来，屏幕上刷出几百行：

```
'hell' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'shell' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'rshell' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'"E:\portable-ai-usb\"' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

`powershell` 这个词被从中间吃掉了，只剩 `hell`、`shell`、`rshell`。
再往后解析器彻底失去同步，开始执行文件里的随机片段。

### 原因

`cmd.exe` 按**系统 ANSI 码页**（简体中文 Windows 是 GBK / 936）切词。
而 `.bat` 文件是 UTF-8 存的 —— 一个汉字 3 个字节。

当某个 UTF-8 字节落在 GBK 的双字节首字节区间（`0x81`–`0xFE`）时，
cmd 会认为"这个字节要和下一个字节合成一个字符"，于是**吞掉后一个字节**。
整个词法分析从头错位。

关键发现：**这不是长度问题，是多字节特有的问题。**

当时的实测数据：

| 行类型 | 字节数 | 结果 |
|---|---|---|
| 纯 ASCII 的 powershell 调用行 | 75–104 | 全部正常 |
| 中文菜单行 | 72–90 | 从 90 字节那行开始必炸 |

纯 ASCII 行再长也没事，中文行一到某个长度就崩。

### 修法

**别跟 cmd 斗。** 把中文界面整个搬进 PowerShell，`.bat` 只留纯 ASCII 转发：

```bat
@echo off
chcp 65001 >nul 2>&1
powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0tools\menu.ps1"
```

这样 `.bat` 里一个非 ASCII 字符都没有，cmd 怎么切都不会错。

同理，`chcp 65001` 只解决**输出显示**，解决不了**解析** —— 这两件事经常被混为一谈。

## 二、换行符：`.bat` 必须 CRLF

### 现象

本地跑得好好的，从 GitHub 克隆下来就报第一章那串错。

### 原因

建仓时设了 `core.autocrlf false`，`.bat` 以 LF 存进仓库、也以 LF 检出。
`cmd.exe` 解析 `goto` / 标签时对 LF 不容忍，会丢字符。

### 实测对照

把同一份菜单 `.bat` 存成两个版本，各跑一遍，数特征碎片：

| 换行符 | 特征碎片命中数 |
|---|---|
| CRLF | **0** |
| LF | **9 / 9**（`hell` `shell` `rshell` `ell` `lftest` `ig` `mall` `robe` `top`） |

### 修法

用 `.gitattributes` 锁死，别指望每台机器上的 `core.autocrlf` 配置：

```gitattributes
* text=auto eol=lf
*.bat text eol=crlf
*.ps1 text eol=crlf
*.png binary
*.gguf binary
*.dll binary
*.exe binary
```

**注意顺序** —— git 是**最后一条匹配的规则赢**。`*` 必须写在最前面，
否则后面那条 `*.bat` 会被它覆盖。

顺带一个验证点：即使仓库里存的是 LF，`.gitattributes` 在 GitHub 的
"Download ZIP" 归档里也会生效。所以下载 ZIP 的用户拿到的是 CRLF，
这条路是通的 —— 但值得亲自验一次，别假设。

## 三、`.ps1` 要带 BOM，`.bat` 不能带

两个方向相反，很容易搞混：

- **PowerShell 5.1 读没有 BOM 的 `.ps1`**，会按系统 ANSI 码页解码。
  脚本里的中文**读进去就是错的** —— 这不是显示乱码，是字符串内容本身就错了，
  后续任何比较、拼接都会跟着错。
- **`.bat` 带 BOM**，那三个字节会被当成一条命令去执行，报错。

麻烦在于：**很多编辑器（包括一些 AI 编程工具）保存时会默默去掉 BOM。**
改完必须自己验：

```powershell
$b = [IO.File]::ReadAllBytes("launcher.ps1")
$hasBom = ($b[0] -eq 0xEF) -and ($b[1] -eq 0xBB) -and ($b[2] -eq 0xBF)
```

## 四、PowerShell 的四个隐雷

### 1. `-notmatch` 对数组返回的是元素，不是布尔

这个最阴。

```powershell
$gpuNames = @("NVIDIA RTX 5070 Ti Laptop", "AMD Radeon 610M")

if ($gpuNames -notmatch "NVIDIA") {
    # 跳过 CUDA  ——  但这里永远会进来！
}
```

`$gpuNames -notmatch "NVIDIA"` 不返回 `$true` / `$false`，
它返回**所有不匹配的元素**组成的数组：`@("AMD Radeon 610M")`。

非空数组在 `if` 里是真 —— 于是双显卡机器（N 卡 + 核显）永远判定"没有 N 卡"，
直接跳过 CUDA 走 CPU。单显卡机器反而正常，所以特别难发现。

正确写法：

```powershell
$hasNvidia = [bool]@($gpuNames | Where-Object { $_ -match '(?i)nvidia' }).Count
```

### 2. 变量名大小写不敏感

新增一个参数叫 `$Model`，而脚本里早就有一个 `$model`（是个 `FileInfo` 对象）——
PowerShell 认为它们是**同一个变量**。

参数一传进来，`FileInfo` 就被覆盖成字符串，紧接着 `$model.Name` 和 `$model.FullName`
全是空的。改成 `-ModelName` 才好。

### 3. `$args`、`$Profile`、`$Host`、`$Error` 是自动变量

不能拿它们当 `param()` 名。用了会得到一个很难看的报错，或者更糟 —— 悄悄不生效。

### 4. 字符串里的 `$i:` 会被当成作用域限定符

```powershell
"第$i段: 正在下载"     # 报错，$i: 被解析为 $i 的 scope
"第${i}段: 正在下载"   # 正确
```

## 五、`llama-server.exe` 只有 9 KB

### 现象

在干净的 Windows 上双击启动，窗口一闪就退，日志里什么都没有。

### 原因

`llama-server.exe` 是个 **9,216 字节的转发壳**，真正的实现在
`llama-server-impl.dll`（8.9 MB）里。这个壳 import 了 `VCRUNTIME140.dll`。

顺序是这样的：

1. Windows 的 DLL 搜索顺序里，**应用程序所在目录排第一位**，`System32` 排第二。
2. 但 `System32` 里**没有** `vcruntime140.dll` —— 它属于 VC++ 可再发行组件，
   要单独安装才会被放进系统目录。
3. 不装、又不在应用目录里 → 找不到 → 进程直接退出。

（`msvcp_win.dll` 不一样，它是 Windows 自带的系统组件，那个从 `System32` 加载是正常的。）

### 修法

**app-local 部署** —— 把运行库 DLL 直接拷到 exe 旁边。
因为应用目录在搜索顺序里排第一，放在这里就是最优先被找到的位置，
**完全不用碰宿主系统**（不需要管理员权限，不装任何东西）：

```
vcruntime140.dll            vcruntime140_1.dll
vcruntime140_threads.dll    msvcp140.dll
msvcp140_1.dll              msvcp140_2.dll
msvcp140_atomic_wait.dll    msvcp140_codecvt_ids.dll
concrt140.dll               vcomp140.dll
```

### 怎么确认真的生效

**不是看文件在不在，是看实际加载路径。**

```powershell
$p = Start-Process "E:\llama.cpp\cuda13\llama-server.exe" `
     -ArgumentList "--version" -PassThru -WindowStyle Hidden
Start-Sleep -Seconds 2
$p.Modules | Where-Object { $_.ModuleName -match 'vcruntime|msvcp' } |
    Select-Object ModuleName, FileName
```

要看到 `FileName` 指向 `E:\llama.cpp\cuda13\vcruntime140.dll` 才算成。
如果显示的是 `C:\Windows\System32\...`，说明这台机器本来就装过 VC++ 运行库 ——
换到没装过的机器上还是会挂。**必须找一台干净的机器复验。**

## 六、断点续传把文件下坏了

### 现象

下载完成，SHA-256 对不上。

### 原因

某些 GitHub 加速镜像**忽略 `Range` 请求头**。
你发 `Range: bytes=1000000-`，它照样从第 0 字节开始重发整个文件。
`curl -C -` 是"追加"语义，于是把完整文件追加到了已下载的部分后面。

实测结果：

| 包 | 症状 |
|---|---|
| cpu | 文件长度**超出 278,528 字节** |
| vulkan | 长度**恰好正确**，但 SHA-256 错（内容被覆盖） |

第二种更危险 —— 长度对了，肉眼看不出来。

### 修法

1. **续传走直连** `github.com`（实测它尊重 `Range`），镜像只用来看元信息。
2. **每一步都校验**。GitHub API 的每个 release asset 都自带 `digest`：

```powershell
(Invoke-RestMethod "https://api.github.com/repos/ggml-org/llama.cpp/releases/tags/b11270").assets |
    Select-Object name, size, digest
```

3. 哈希对不上就**删掉重下**，不要用 `-C -` 硬续 —— 你已经不知道文件里是什么了。

## 七、别用 `taskkill /IM` 停服务

```powershell
taskkill /F /IM llama-server.exe        # ← 会杀掉这台机器上所有同名进程
```

在别人的电脑上这是事故级的：用户可能正开着自己的一份在跑，
你为了停掉 U 盘上的服务，把人家的也干掉了。

### 修法

按**可执行文件路径**过滤，只动自己盘里的：

```powershell
Get-Process llama-server -ErrorAction SilentlyContinue | Where-Object {
    $_.Path -and $_.Path.StartsWith($Root, [StringComparison]::OrdinalIgnoreCase)
} | Stop-Process -Force
```

### 怎么验证

同时启动两个：宿主机的（`D:\...`）和 U 盘的（`E:\...`），然后跑停止命令。

期望输出：

```
跳过 PID 11248（不属于本 U 盘）：D:\llama.cpp\llama-b11270-bin-win-cuda-13.4-x64\llama-server.exe
已停止 PID 15576  E:\llama.cpp\cuda13\llama-server.exe
已停止 1 个；跳过 1 个不属于本 U 盘的进程。
```

## 八、FAT32 装不下 6.4 GB 的模型

FAT32 单个文件上限 **4 GB**。9B 模型的 Q5_K_M 量化是 6.4 GB —— 直接拷不进去，
Windows 会报"文件过大"。

**格式化时选 exFAT。** 理由：

- 没有 4 GB 单文件限制
- Windows / macOS / Linux 都能读写
- 相比之下 NTFS 在 macOS 上写入支持很差

代价：exFAT 不支持备用数据流（ADS），所以"从网上下载的文件被标记"这件事不落盘 ——
对本项目反而是好事，见下一条。

## 九、CUDA 12.4 上不了 Blackwell

RTX 50 系是 Blackwell，计算能力 `sm_120`，需要 **CUDA 12.8 及以上**才编得出内核。
拿 CUDA 12.4 编译的 llama.cpp 在这张卡上会识别到显卡但用不起来，退回 CPU。

**教训不是"要用新版 CUDA"，而是"别按'多带一套总没坏处'堆包"。**
当时本来准备了三套（CUDA 12.4 / CUDA 13.4 / Vulkan / CPU），
发现 CUDA 12.4 在目标机器上纯属占 624 MB 的死重之后砍掉了 —— 老 N 卡交给 Vulkan 兜底。

**装了不能用，就是纯体积。**

## 十、显存未知时不要乐观

启动器的显存分档逻辑原来按 GPU 型号名去猜，猜错就 OOM。
在陌生机器上型号识别失败是常事 —— 尤其是核显、虚拟显卡、老驱动。

### 修法

**拿不到显存就按最保守来**：上下文压到 8192、KV cache 用 `q4_0`，
并且**打印一行说明为什么**。静默降级比降级本身更糟。

## 十一、模型名匹配别只做全等

文档里写"文件名不用写全"，代码里只做了 `-eq` 全等匹配。
用户填 `MiMo`、或者漏了 `.gguf` 后缀，就一个都选不到，而且**不报错**——
悄悄退回默认模型，用户完全不知道发生了什么。

### 修法

三级匹配：

1. 全等
2. 全等 + 自动补 `.gguf`
3. 大小写不敏感的子串匹配

**多命中就列出来让用户选，绝不猜。** 猜错模型比报错更让人困惑。

另外：`mmproj-*.gguf` 是多模态投影文件，不是模型本体 ——
挑选和"体积最大"比较时都要排除掉，否则会被当成一个超大模型选中。

## 十二、测试脚本自己的两个坑

### `Read-Host` 在 stdin 被重定向时返回 `null`

不是空字符串，是 `$null`。菜单循环会立刻炸或者空转。
更糟的是在 `$ErrorActionPreference = "Stop"` 下，`Read-Host` 会**直接抛**
"PowerShell 处于非交互模式"，把整个脚本带走 —— 表现不是报错，是菜单渲染一次就消失。

统一封一个 `Read-Choice`：重定向时显式读 `[Console]::In.ReadLine()`，读不到才返回 `$null`，
调用方据此干净退出。

```powershell
function Read-Choice([string]$Prompt) {
    try {
        if ([Console]::IsInputRedirected) {
            $line = [Console]::In.ReadLine()
            if ($null -eq $line) { return $null }
            return $line.Trim()
        }
    } catch { return $null }
    try { return (Read-Host $Prompt).Trim() } catch { return $null }
}
```

### `curl: (23) client returned ERROR on write`

这个报错看着像网络问题，**其实是输出目录不存在**。
`$env:TEMP\xxx` 被系统清理掉之后，`curl -o` 找不到目录就报这个。
先 `New-Item -ItemType Directory -Force` 就好。

## 十三、数组 splat 是按位置传参的（菜单 9 个选项静默失效）

### 现象

在菜单里选 `[11] 测一下这支 U 盘的速度`，**弹出来的是一台服务器在加载模型**。
选 `[1]` 到 `[5]` 也是同样结果 —— 都是"启动一个模型服务器"，
只不过上下文大小全用了默认值。

没有任何报错。`-Bench` 明明传进去了，脚本就是当没看见。

### 原因

原来的转发是这样的：

```powershell
function Invoke-Launcher { param([string[]]$ExtraArgs) & $Launcher @ExtraArgs }
Invoke-Launcher @('-Bench')
```

PowerShell 的数组 splat `@array` 是**按位置**传参，不是按名字。
字符串 `"-Bench"` 不是"一个叫 -Bench 的开关"，而是"第一个位置参数的值"。
于是它被绑到 `$Backend` 上，`$Bench` 永远是 `$False`。

同一个函数里 `@('-Backend','vulkan')` 形式的调用也一样：
`"-Backend"` 变成 `$Backend` 的值，`"vulkan"` 变成 `$Ctx` 的值。

### 修法

写死参数名，直接调用：

```powershell
& $Launcher -Bench
& $Launcher -Backend vulkan -Ctx 32768
```

静态可查，不可能错。这个缺陷在 v1.0.0 就存在，
一直到 `[11]` 被做出来、行为差异足够显眼才被发现 ——
在此之前 `[1]`~`[5]` 一直是"能跑，只是参数没生效"，
而默认参数恰好就是常用的那个，所以没人察觉。

### 教训

**"参数被静默忽略"比"参数报错"难发现得多。**
凡是用 splat 转发参数的地方，都值得写一个"传了参数 vs 没传参数，行为应当不同"的对照测试。

## 十四、`chcp 65001` 会吃掉重定向进来的 stdin

### 现象

同一个脚本，直接跑正常，经 `.bat` 跑就只渲染一次菜单然后退出：

```bat
@echo off
chcp 65001 >nul          ← 就是这一行
cd /d "%~dp0"
powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0tools\menu.ps1" %*
```

### 原因

`chcp` 在设置代码页时会读标准输入。当 stdin 来自重定向（管道、计划任务、
自动化测试的 `< file`）时，它把整个输入流读空了 —— 后面的脚本再也读不到任何字符，
`Read-Choice` 拿到 `$null`，干净退出。

最小复现：

```bat
@echo off
chcp 65001 >nul
powershell -NoProfile -File probe.ps1        :: probe.ps1 读 [Console]::In.ReadLine()
```

```
输入 6\r\nq\r\n：
  带 chcp  → 读到 []
  不带 chcp → 读到 [6]
```

### 修法

只给 `chcp` 自己接一个空输入，它就没得吃了：

```bat
chcp 65001 >nul < nul
```

代码页照常生效（中文照样正常显示），调用方的 stdin 原封不动。

### 教训

**入口脚本里任何会碰标准输入的命令都是嫌疑犯。**
这类 bug 只在"非交互运行"时出现，而人工双击测试永远碰不到它。

## 怎么确认真的修好了

不是"看起来没报错"。这个项目里用过的验证手段：

| 改动 | 验证方式 |
|---|---|
| cmd 解析 | 两种换行符各跑一遍，**数特征碎片命中数**，不是靠眼看 |
| 换行符 | 从 GitHub 下载 ZIP 解出来，确认 `.bat` 是 CRLF |
| 运行库 | 查进程**实际加载的 DLL 路径**，不是看文件存不存在 |
| 进程过滤 | 同时起两个同名进程，确认只死一个 |
| 下载完整性 | 用 API 给的 `digest` 当基准，回下载再比一次 |
| 发布产物 | 把 Release 附件下载回来，SHA-256 对上才算发完 |
| 同步 | 仓库和 U 盘**逐字节比对**，不是看时间戳 |
| 参数转发 | 传参数与不传参数**行为必须不同**，照抄一遍菜单每个分支 |
| 测速准确性 | **连测三次看数字是否稳定** —— 虚高的缓存值每次都不同 |
| 非交互行为 | 用 `< file` 喂输入走**真实入口**（`.bat`），不是直接调脚本 |
| 真机 | 找一台**从没装过开发工具**的电脑实测 |

最后一条最重要。本项目 README 里那条"在一台全新的 Windows 11 笔记本上实测通过"，
是整个清单里最有含金量的一行 —— 因为前面所有验证都可能被"我这台机器恰好有环境"骗过去。
