# 把一个 9B 大模型装进 U 盘：踩坑记录

这是 [portable-ai-usb](https://github.com/KAYOYAK/portable-ai-usb) 的开发过程记录。

如果你正在做类似的事（把本地大模型塞进移动介质、在陌生电脑上跑起来），
下面这些坑你大概率会撞上。每一条都写了**报错原文**，方便你搜到这里。

目前 19 条。前十条是 Windows 侧的（PowerShell 5.1、cmd.exe、exFAT），
第十五、十六条是给 macOS / Linux 那份 bash 启动器踩的 —— bash 的坑和 PowerShell 完全是两套
（跨函数传值、退出码语义），别把一边的经验直接搬过去。
最后三条（十七~十九）跟平台无关，讲的是**怎么确认自己改对了**：测的是哪份文件、
提示词该怎么说、参数列表为什么不能手抄。

## 一、cmd.exe 会把带中文的 `.bat` 解析错位

### 现象

双击运行，菜单没出来，屏幕上刷出几百行：

```
'hell' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'shell' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'rshell' 不是内部或外部命令，也不是可运行的程序或批处理文件。
'"E:\portable-ai-usb\"' 不是内部或外部命令，也不是可运行的程序或批处理文件。
```

`powershell` 这个词被从中间吃掉了，只剩 `hell`、`shell`、`rshell`。
再往后解析器彻底失去同步，开始执行文件里的随机片段。

### 原因

`cmd.exe` 按**系统 ANSI 码页**（简体中文 Windows 是 GBK / 936）切词。
而 `.bat` 文件是 UTF-8 存的 —— 一个汉字 3 个字节。

当某个 UTF-8 字节落在 GBK 的双字节首字节区间（`0x81`–`0xFE`）时，
cmd 会认为"这个字节要和下一个字节合成一个字符"，于是**吞掉后一个字节**。
整个词法分析从头错位。

关键发现：**这不是长度问题，是多字节特有的问题。**

当时的实测数据：

| 行类型 | 字节数 | 结果 |
|---|---|---|
| 纯 ASCII 的 powershell 调用行 | 75–104 | 全部正常 |
| 中文菜单行 | 72–90 | 从 90 字节那行开始必炸 |

纯 ASCII 行再长也没事，中文行一到某个长度就崩。

### 修法

**别跟 cmd 斗。** 把中文界面整个搬进 PowerShell，`.bat` 只留纯 ASCII 转发：

```bat
@echo off
chcp 65001 >nul 2>&1
powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0tools\menu.ps1"
```

这样 `.bat` 里一个非 ASCII 字符都没有，cmd 怎么切都不会错。

同理，`chcp 65001` 只解决**输出显示**，解决不了**解析** —— 这两件事经常被混为一谈。

## 二、换行符：`.bat` 必须 CRLF

### 现象

本地跑得好好的，从 GitHub 克隆下来就报第一章那串错。

### 原因

建仓时设了 `core.autocrlf false`，`.bat` 以 LF 存进仓库、也以 LF 检出。
`cmd.exe` 解析 `goto` / 标签时对 LF 不容忍，会丢字符。

### 实测对照

把同一份菜单 `.bat` 存成两个版本，各跑一遍，数特征碎片：

| 换行符 | 特征碎片命中数 |
|---|---|
| CRLF | **0** |
| LF | **9 / 9**（`hell` `shell` `rshell` `ell` `lftest` `ig` `mall` `robe` `top`） |

### 修法

用 `.gitattributes` 锁死，别指望每台机器上的 `core.autocrlf` 配置：

```gitattributes
* text=auto eol=lf
*.bat text eol=crlf
*.ps1 text eol=crlf
*.png binary
*.gguf binary
*.dll binary
*.exe binary
```

**注意顺序** —— git 是**最后一条匹配的规则赢**。`*` 必须写在最前面，
否则后面那条 `*.bat` 会被它覆盖。

顺带一个验证点：即使仓库里存的是 LF，`.gitattributes` 在 GitHub 的
"Download ZIP" 归档里也会生效。所以下载 ZIP 的用户拿到的是 CRLF，
这条路是通的 —— 但值得亲自验一次，别假设。

## 三、`.ps1` 要带 BOM，`.bat` 不能带

两个方向相反，很容易搞混：

- **PowerShell 5.1 读没有 BOM 的 `.ps1`**，会按系统 ANSI 码页解码。
  脚本里的中文**读进去就是错的** —— 这不是显示乱码，是字符串内容本身就错了，
  后续任何比较、拼接都会跟着错。
- **`.bat` 带 BOM**，那三个字节会被当成一条命令去执行，报错。

麻烦在于：**很多编辑器（包括一些 AI 编程工具）保存时会默默去掉 BOM。**
改完必须自己验：

```powershell
$b = [IO.File]::ReadAllBytes("launcher.ps1")
$hasBom = ($b[0] -eq 0xEF) -and ($b[1] -eq 0xBB) -and ($b[2] -eq 0xBF)
```

## 四、PowerShell 的四个隐雷

### 1. `-notmatch` 对数组返回的是元素，不是布尔

这个最阴。

```powershell
$gpuNames = @("NVIDIA RTX 5070 Ti Laptop", "AMD Radeon 610M")

if ($gpuNames -notmatch "NVIDIA") {
    # 跳过 CUDA  ——  但这里永远会进来！
}
```

`$gpuNames -notmatch "NVIDIA"` 不返回 `$true` / `$false`，
它返回**所有不匹配的元素**组成的数组：`@("AMD Radeon 610M")`。

非空数组在 `if` 里是真 —— 于是双显卡机器（N 卡 + 核显）永远判定"没有 N 卡"，
直接跳过 CUDA 走 CPU。单显卡机器反而正常，所以特别难发现。

正确写法：

```powershell
$hasNvidia = [bool]@($gpuNames | Where-Object { $_ -match '(?i)nvidia' }).Count
```

### 2. 变量名大小写不敏感

新增一个参数叫 `$Model`，而脚本里早就有一个 `$model`（是个 `FileInfo` 对象）——
PowerShell 认为它们是**同一个变量**。

参数一传进来，`FileInfo` 就被覆盖成字符串，紧接着 `$model.Name` 和 `$model.FullName`
全是空的。改成 `-ModelName` 才好。

### 3. `$args`、`$Profile`、`$Host`、`$Error` 是自动变量

不能拿它们当 `param()` 名。用了会得到一个很难看的报错，或者更糟 —— 悄悄不生效。

### 4. 字符串里的 `$i:` 会被当成作用域限定符

```powershell
"第$i段: 正在下载"     # 报错，$i: 被解析为 $i 的 scope
"第${i}段: 正在下载"   # 正确
```

## 五、`llama-server.exe` 只有 9 KB

### 现象

在干净的 Windows 上双击启动，窗口一闪就退，日志里什么都没有。

### 原因

`llama-server.exe` 是个 **9,216 字节的转发壳**，真正的实现在
`llama-server-impl.dll`（8.9 MB）里。这个壳 import 了 `VCRUNTIME140.dll`。

顺序是这样的：

1. Windows 的 DLL 搜索顺序里，**应用程序所在目录排第一位**，`System32` 排第二。
2. 但 `System32` 里**没有** `vcruntime140.dll` —— 它属于 VC++ 可再发行组件，
   要单独安装才会被放进系统目录。
3. 不装、又不在应用目录里 → 找不到 → 进程直接退出。

（`msvcp_win.dll` 不一样，它是 Windows 自带的系统组件，那个从 `System32` 加载是正常的。）

### 修法

**app-local 部署** —— 把运行库 DLL 直接拷到 exe 旁边。
因为应用目录在搜索顺序里排第一，放在这里就是最优先被找到的位置，
**完全不用碰宿主系统**（不需要管理员权限，不装任何东西）：

```
vcruntime140.dll            vcruntime140_1.dll
vcruntime140_threads.dll    msvcp140.dll
msvcp140_1.dll              msvcp140_2.dll
msvcp140_atomic_wait.dll    msvcp140_codecvt_ids.dll
concrt140.dll               vcomp140.dll
```

### 怎么确认真的生效

**不是看文件在不在，是看实际加载路径。**

```powershell
$p = Start-Process "E:\llama.cpp\cuda13\llama-server.exe" `
     -ArgumentList "--version" -PassThru -WindowStyle Hidden
Start-Sleep -Seconds 2
$p.Modules | Where-Object { $_.ModuleName -match 'vcruntime|msvcp' } |
    Select-Object ModuleName, FileName
```

要看到 `FileName` 指向 `E:\llama.cpp\cuda13\vcruntime140.dll` 才算成。
如果显示的是 `C:\Windows\System32\...`，说明这台机器本来就装过 VC++ 运行库 ——
换到没装过的机器上还是会挂。**必须找一台干净的机器复验。**

## 六、断点续传把文件下坏了

### 现象

下载完成，SHA-256 对不上。

### 原因

某些 GitHub 加速镜像**忽略 `Range` 请求头**。
你发 `Range: bytes=1000000-`，它照样从第 0 字节开始重发整个文件。
`curl -C -` 是"追加"语义，于是把完整文件追加到了已下载的部分后面。

实测结果：

| 包 | 症状 |
|---|---|
| cpu | 文件长度**超出 278,528 字节** |
| vulkan | 长度**恰好正确**，但 SHA-256 错（内容被覆盖） |

第二种更危险 —— 长度对了，肉眼看不出来。

### 修法

1. **续传走直连** `github.com`（实测它尊重 `Range`），镜像只用来看元信息。
2. **每一步都校验**。GitHub API 的每个 release asset 都自带 `digest`：

```powershell
(Invoke-RestMethod "https://api.github.com/repos/ggml-org/llama.cpp/releases/tags/b11270").assets |
    Select-Object name, size, digest
```

3. 哈希对不上就**删掉重下**，不要用 `-C -` 硬续 —— 你已经不知道文件里是什么了。

## 七、别用 `taskkill /IM` 停服务

```powershell
taskkill /F /IM llama-server.exe        # ← 会杀掉这台机器上所有同名进程
```

在别人的电脑上这是事故级的：用户可能正开着自己的一份在跑，
你为了停掉 U 盘上的服务，把人家的也干掉了。

### 修法

按**可执行文件路径**过滤，只动自己盘里的：

```powershell
Get-Process llama-server -ErrorAction SilentlyContinue | Where-Object {
    $_.Path -and $_.Path.StartsWith($Root, [StringComparison]::OrdinalIgnoreCase)
} | Stop-Process -Force
```

### 怎么验证

同时启动两个：宿主机的（`D:\...`）和 U 盘的（`E:\...`），然后跑停止命令。

期望输出：

```
跳过 PID 11248（不属于本 U 盘）：D:\llama.cpp\llama-b11270-bin-win-cuda-13.4-x64\llama-server.exe
已停止 PID 15576  E:\llama.cpp\cuda13\llama-server.exe
已停止 1 个；跳过 1 个不属于本 U 盘的进程。
```

## 八、FAT32 装不下 6.4 GB 的模型

FAT32 单个文件上限 **4 GB**。9B 模型的 Q5_K_M 量化是 6.4 GB —— 直接拷不进去，
Windows 会报"文件过大"。

**格式化时选 exFAT。** 理由：

- 没有 4 GB 单文件限制
- Windows / macOS / Linux 都能读写
- 相比之下 NTFS 在 macOS 上写入支持很差

代价：exFAT 不支持备用数据流（ADS），所以"从网上下载的文件被标记"这件事不落盘 ——
对本项目反而是好事，见下一条。

## 九、CUDA 12.4 上不了 Blackwell

RTX 50 系是 Blackwell，计算能力 `sm_120`，需要 **CUDA 12.8 及以上**才编得出内核。
拿 CUDA 12.4 编译的 llama.cpp 在这张卡上会识别到显卡但用不起来，退回 CPU。

**教训不是"要用新版 CUDA"，而是"别按'多带一套总没坏处'堆包"。**
当时本来准备了三套（CUDA 12.4 / CUDA 13.4 / Vulkan / CPU），
发现 CUDA 12.4 在目标机器上纯属占 624 MB 的死重之后砍掉了 —— 老 N 卡交给 Vulkan 兜底。

**装了不能用，就是纯体积。**

## 十、显存未知时不要乐观

启动器的显存分档逻辑原来按 GPU 型号名去猜，猜错就 OOM。
在陌生机器上型号识别失败是常事 —— 尤其是核显、虚拟显卡、老驱动。

### 修法

**拿不到显存就按最保守来**：上下文压到 8192、KV cache 用 `q4_0`，
并且**打印一行说明为什么**。静默降级比降级本身更糟。

## 十一、模型名匹配别只做全等

文档里写"文件名不用写全"，代码里只做了 `-eq` 全等匹配。
用户填 `MiMo`、或者漏了 `.gguf` 后缀，就一个都选不到，而且**不报错**——
悄悄退回默认模型，用户完全不知道发生了什么。

### 修法

三级匹配：

1. 全等
2. 全等 + 自动补 `.gguf`
3. 大小写不敏感的子串匹配

**多命中就列出来让用户选，绝不猜。** 猜错模型比报错更让人困惑。

另外：`mmproj-*.gguf` 是多模态投影文件，不是模型本体 ——
挑选和"体积最大"比较时都要排除掉，否则会被当成一个超大模型选中。

### 补记：放宽匹配之后，两边比的得是同一个东西

上面这套三级匹配，Windows 那份（PowerShell）是好的，照着它写的 macOS / Linux 那份
（`启动AI.sh`）却是坏的 —— 坏在一个很隐蔽的地方：**"取出全部模型"这个函数吐的是绝对路径，
而三条规则拿的是裸文件名。**

于是：

- 第一、二档（全等、补 `.gguf`）拿 `A.gguf` 去比 `/Volumes/AI/models/A.gguf`，**永远不命中**。
  用户老老实实写全文件名，反而得到一句"匹配到多个模型"。
- 第三档（子串）拿整条**路径**去比。盘挂载在 `/Volumes/AI/`，
  那么 `--model ai` 就会命中，并且**静默选中**某个模型，界面上还标着"命令行 --model 指定"。

放宽匹配是为了"不用写全也能命中"，但放宽的同时把**比较口径**也放歪了 ——
前者是功能，后者是 bug，而且它俩长在同一段代码里。

**修法**：匹配之前统一剥成 `basename`，三条规则都比文件名。命中了再输出全路径。
顺带把三条规则都做成大小写不敏感，对齐 PowerShell 那边 `-eq` 的实际语义。

**可迁移的判断**：凡是"A 列表里的元素"和"B 输入"要比对，先确认两边是同一类东西 ——
名字对名字，路径对路径。写的时候看不出问题，因为两种写法在只有一个模型、
且路径里不含关键词时**结果一样**。

## 十二、测试脚本自己的两个坑

### `Read-Host` 在 stdin 被重定向时返回 `null`

不是空字符串，是 `$null`。菜单循环会立刻炸或者空转。
更糟的是在 `$ErrorActionPreference = "Stop"` 下，`Read-Host` 会**直接抛**
"PowerShell 处于非交互模式"，把整个脚本带走 —— 表现不是报错，是菜单渲染一次就消失。

统一封一个 `Read-Choice`：重定向时显式读 `[Console]::In.ReadLine()`，读不到才返回 `$null`，
调用方据此干净退出。

```powershell
function Read-Choice([string]$Prompt) {
    try {
        if ([Console]::IsInputRedirected) {
            $line = [Console]::In.ReadLine()
            if ($null -eq $line) { return $null }
            return $line.Trim()
        }
    } catch { return $null }
    try { return (Read-Host $Prompt).Trim() } catch { return $null }
}
```

### `curl: (23) client returned ERROR on write`

这个报错看着像网络问题，**其实是输出目录不存在**。
`$env:TEMP\xxx` 被系统清理掉之后，`curl -o` 找不到目录就报这个。
先 `New-Item -ItemType Directory -Force` 就好。

## 十三、数组 splat 是按位置传参的（菜单 9 个选项静默失效）

### 现象

在菜单里选 `[11] 测一下这支 U 盘的速度`，**弹出来的是一台服务器在加载模型**。
选 `[1]` 到 `[5]` 也是同样结果 —— 都是"启动一个模型服务器"，
只不过上下文大小全用了默认值。

没有任何报错。`-Bench` 明明传进去了，脚本就是当没看见。

### 原因

原来的转发是这样的：

```powershell
function Invoke-Launcher { param([string[]]$ExtraArgs) & $Launcher @ExtraArgs }
Invoke-Launcher @('-Bench')
```

PowerShell 的数组 splat `@array` 是**按位置**传参，不是按名字。
字符串 `"-Bench"` 不是"一个叫 -Bench 的开关"，而是"第一个位置参数的值"。
于是它被绑到 `$Backend` 上，`$Bench` 永远是 `$False`。

同一个函数里 `@('-Backend','vulkan')` 形式的调用也一样：
`"-Backend"` 变成 `$Backend` 的值，`"vulkan"` 变成 `$Ctx` 的值。

### 修法

写死参数名，直接调用：

```powershell
& $Launcher -Bench
& $Launcher -Backend vulkan -Ctx 32768
```

静态可查，不可能错。这个缺陷在 v1.0.0 就存在，
一直到 `[11]` 被做出来、行为差异足够显眼才被发现 ——
在此之前 `[1]`~`[5]` 一直是"能跑，只是参数没生效"，
而默认参数恰好就是常用的那个，所以没人察觉。

### 教训

**"参数被静默忽略"比"参数报错"难发现得多。**
凡是用 splat 转发参数的地方，都值得写一个"传了参数 vs 没传参数，行为应当不同"的对照测试。

## 十四、`chcp 65001` 会吃掉重定向进来的 stdin

### 现象

同一个脚本，直接跑正常，经 `.bat` 跑就只渲染一次菜单然后退出：

```bat
@echo off
chcp 65001 >nul          ← 就是这一行
cd /d "%~dp0"
powershell -NoProfile -ExecutionPolicy Bypass -File "%~dp0tools\menu.ps1" %*
```

### 原因

`chcp` 在设置代码页时会读标准输入。当 stdin 来自重定向（管道、计划任务、
自动化测试的 `< file`）时，它把整个输入流读空了 —— 后面的脚本再也读不到任何字符，
`Read-Choice` 拿到 `$null`，干净退出。

最小复现：

```bat
@echo off
chcp 65001 >nul
powershell -NoProfile -File probe.ps1        :: probe.ps1 读 [Console]::In.ReadLine()
```

```
输入 6\r\nq\r\n：
  带 chcp  → 读到 []
  不带 chcp → 读到 [6]
```

### 修法

只给 `chcp` 自己接一个空输入，它就没得吃了：

```bat
chcp 65001 >nul < nul
```

代码页照常生效（中文照样正常显示），调用方的 stdin 原封不动。

### 教训

**入口脚本里任何会碰标准输入的命令都是嫌疑犯。**
这类 bug 只在"非交互运行"时出现，而人工双击测试永远碰不到它。

## 十五、命令替换会开子 shell，函数里设的变量传不回来

### 现象

给 macOS / Linux 写的 `启动AI.sh` 里，模型名匹配分了三种结果：唯一命中、多命中、没命中。
想让函数把"是哪一种"告诉调用方，于是函数里设了两个全局变量：

```sh
resolve_model() {
    ...
    if [ "$n" -eq 0 ]; then RESOLVE_ERR="notfound"; else RESOLVE_ERR="multi"; fi
    RESOLVE_HITS="$hits"
    return 1
}
```

调用方这样用：

```sh
if MODEL="$(resolve_model "$MODEL_NAME")"; then
    SOURCE="命令行指定"
else
    if [ "$RESOLVE_ERR" = "multi" ]; then
        err "匹配到多个模型"
    else
        err "找不到"
    fi
fi
```

测下来：**不管一个都没匹配到还是匹配到多个，永远打印「找不到」。**
`RESOLVE_ERR` 在调用方那边永远是空的。

### 原因

`$( ... )` 是**命令替换**，它会 fork 一个子 shell 去跑里面的东西。
函数在子 shell 里执行，`RESOLVE_ERR=...` 改的是子 shell 的变量；
子 shell 结束、把 stdout 交回来的时候，那些变量一起没了。

这和 PowerShell 的 `$( )` 或 `& { }` 不一样 —— PowerShell 里脚本块默认还在同一个作用域，
bash 的 `$( )` 是实打实的新进程。

顺带一个同源的坑：**赋值语句即使右边失败了也照样赋值**。
`MODEL="$(resolve_model ...)"` 在函数 `return 1` 时，`MODEL` 依然会被填上
stdout 的全部内容 —— 多命中时那是一整列文件名，后面 `-m "$MODEL"` 会把这坨东西
当成路径喂给引擎。要先用一个普通变量接住、看返回码、再决定赋不赋。

### 修法

用**返回码**表达结果，用 **stdout** 表达数据，两者都不受子 shell 影响：

```sh
resolve_model() {
    ...
    [ -n "$hits" ] || return 2        # 没命中
    n="$(printf '%s\n' "$hits" | grep -c . 2>/dev/null || true)"
    [ "$n" -eq 1 ] && { printf '%s\n' "$hits"; return 0; }   # 唯一命中
    printf '%s\n' "$hits"
    return 1                          # 多命中，stdout 是所有候选
}
```

调用方接住再分支：

```sh
out="$(resolve_model "$MODEL_NAME")"; rc=$?
case "$rc" in
    0) MODEL="$out"; SOURCE="命令行指定" ;;
    1) err "匹配到多个："; show_candidates "$out"; exit 1 ;;
    *) err "找不到"; exit 1 ;;
esac
```

**怎么验证**：故意让三种情况各跑一遍 —— 完整文件名（应命中 1）、
`--model Qwen`（盘里两个文件名都含 `Qwen`，应列出两个候选）、
`--model 不存在的`（应报找不到）。**三者必须给出三种不同的输出**，
只测"能跑通"是看不出这个 bug 的 —— 它三种情况全都"能跑通"，只是答案都一样。

### 教训

bash 里跨函数传结果，只用两样东西：**返回码**和 **stdout**。
"设个全局变量让外面读"这件事在 PowerShell 里成立，在 bash 里只要调用点被 `$( )` 包住就不成立。

## 十六、`grep -c` 匹配到 0 个时，退出码是 1

### 现象

上面那段修复的初版里写了一行：

```sh
n="$(printf '%s\n' "$hits" | grep -c . 2>/dev/null || printf '0')"
```

本意是"数命中了几行，数不出来就当 0"。结果 `$n` 变成了两行：

```
启动AI.sh: line 247: [: 0
0: integer expected
```

### 原因

`grep` 的退出码语义不是"有没有出错"，而是**"有没有匹配到"**。
`grep -c` 匹配到 0 个时，它会：

- 往 stdout 打印 `0`（这是我们要的）
- 以**退出码 1** 结束（表示"没匹配到"）

于是 `|| printf '0'` 被触发，又往 stdout 追加了第二个 `0`。
命令替换拿到的是整个 stdout：`"0\n0"`，后面 `[ "$n" -eq 0 ]` 直接报
`integer expected`。

同一个坑还有一个更常见的形态：`set -e` 开着的时候，
`grep -c` 数到 0 会让整个脚本静默退出 —— 明明只是想数个数。

### 修法

后面接 `|| true` 而不是 `|| printf '0'` —— 只把退出码抹平，不要再往 stdout 写东西：

```sh
n="$(printf '%s\n' "$hits" | grep -c . 2>/dev/null || true)"
```

要更稳的话用 `awk` 代替，它的退出码不受匹配数影响：

```sh
n="$(printf '%s\n' "$hits" | awk 'END{print NR}')"
```

### 教训

**"命令是否成功"和"命令的输出"是两回事。** 在 `$( ... )` 里，
`||` 右侧的东西会混进结果里。凡是 `$(cmd || fallback)` 的写法，
先问一句：`cmd` 失败时会不会**一边失败一边正常输出**？会的话，fallback 只能改退出码，不能写 stdout。

## 十七、测试"复现"了一个已经修好的 bug

这一节的教训不是关于代码的，是关于**怎么确认自己测的是哪个文件**。

给一个脚本做完修补之后，我造了一棵假 U 盘树来验证，结果测试**完美复现了**那个 bug。
差一点就回头去改一段已经改好的代码。

真正的原因是：那棵测试树是**上一个环节留下的**，里面的脚本是修补前的快照。
测试脚本没有重新拷贝源文件，于是它诚实地、可复现地，测了一份旧文件。

### 怎么发现是测试树的问题

不是靠"再看一眼"，是靠**比哈希**：

```
测试树里的启动AI.sh: 21454 字节  md5 4A8FA269...
源文件             : 28778 字节  md5 79BDAB44...
```

文件名一样、能跑、行为"符合预期"—— 三个信号全都指向"这是新版本"，只有哈希说不是。

### 教训

**"测试跑出预期结果"不等于"测的是当前代码"。** 尤其是当测试树是跨轮次复用的、
或者由另一个 agent / 另一次会话留下的。做法：

1. 造测试环境时**总是从源目录重新拷贝**，不要复用上一次留下的树；
2. 出结论之前，把测试里的那份文件和源文件**比一次哈希**，或者至少在结果里打印
   两者的体积 / 哈希；
3. 反过来说：一个"看不懂为什么修了还坏"的现象，先怀疑测试环境，再怀疑修复。

同源的坑还有一个：那次我在同一段脚本里写了个 `$t` 变量，
PowerShell 把它当成了类型别名（`[System.Management.Automation.TypeAccelerators]`），
整个脚本**解析失败** —— 而 PowerShell 是先把整段解析完再执行的，
所以那一次 `Copy-Item` 根本没跑。命令没跑，和命令跑了但没生效，看起来一模一样。

## 十八、系统提示「说什么」比「说不说」重要得多

### 现象

想让这个 9B 模型默认说中文。模板机制接通了、prompt 里确实有那段话，模型还是用英文回。

### 怎么确认机制没问题

不能靠"回答的语言"判断，那会把模型的不听话误判成代码坏了。
用 `--log-prompts-dir` 把引擎**实际渲染出来的 prompt** 落盘：

```
<|im_start|>system
你必须始终使用简体中文回答，无论用户用什么语言提问。<|im_end|><|im_start|>user
What is the capital of France?<|im_end|><|im_start|>assistant
```

system 消息在，位置对，没有重复。**机制是对的，是模型没听。**

### 那就换说法

同一个模型、同一个问题，六种说法各跑 2~4 次：

| 说法 | 中文回复率 |
|---|---|
| 你必须始终使用简体中文回答，无论用户用什么语言提问。 | 0/2 |
| 始终用简体中文回答。 | 0/2 |
| 无论用户用什么语言提问，你都只能用简体中文回答，不要使用英文。 | 0/2 |
| 你是中文助手，回答一律使用简体中文，禁止英文。 | 0/2 |
| 优先用简体中文回答；用户明确指定别的语言时听用户的。 | 0/3 |
| **中文回答。回答必须全部是简体中文，不要出现英文单词。** | **4/4** |

前五种都是"有礼貌、有条件、有从句"的长句。第六种是短祈使句、动词开头、没有条件从句。

**9B 这个量级的模型对长句里的约束基本不理会。** 如果只测了第一种就下结论，
得到的会是"这个模型根本不听系统提示" —— 而实际上它听，只是那句话得短。

### 顺带验的三条边界

| 情形 | 结果 |
|---|---|
| 客户端自带 system（要求回法文） | 回法文 —— 客户端优先，没被覆盖 |
| 用户明说 `Answer in English` | 回英文 —— 不跟用户抢 |
| 换个模型、`templates/` 里没有对应模板 | 不注入，并在启动信息里说明原因 |

第三条是刻意的：模板是按模型名匹配的，拿一份格式不配套的模板去渲染，
输出会整段烂掉。宁可少一个功能。

## 十九、手抄一遍的参数列表，会安静地少东西

启动器里有一段"显存不够就降档重试"的逻辑，重试时要把引擎参数重新拼一遍。
当时是**手抄**的：

```powershell
$llamaArgs = @()
foreach ($a in @("-m", $model.FullName, "--alias", $alias, "--host", $lanArg,
                 "--port", "$Port", "--n-gpu-layers", "0", ...)) { $llamaArgs += $a }
if ($LoadMode -ne "auto") { $llamaArgs += @("-lm", $LoadMode) }
if ($mmproj) { $llamaArgs += @("-mm", $mmproj.FullName) } else { $llamaArgs += @("--no-mmproj") }
if ($Lan -and $ApiKey) { $llamaArgs += @("--api-key", $ApiKey) }
```

这段抄得很认真，一条不漏。问题是**它抄的是当时的参数列表**。

之后每次新增一个开关（多模态、默认系统提示、局域网钥匙），都要记得在两处同时加。
少加一处，症状是：**正常启动一切正常，只有在显存不够自动降档之后，那个功能才悄悄消失。**
没人会去测这种组合。

### 修法

抽成一个函数，两边都调它：

```powershell
function Build-Args { ... return $a }
$llamaArgs = Build-Args        # 首次
$llamaArgs = Build-Args        # 降档后（配置变量已经改过了）
```

判据很简单：**同一份参数，出现了两次以上，就不该有两个地方在拼它。**

同类的还有 `--host`：Windows 侧和 bash 侧各写了一遍，"局域网"这个功能就得在两处
分别接上监听地址。功能对齐的时候漏掉一边，症状是"Mac 上能用手机连，Windows 上不行"。

## 二十、引擎在中文目录名下会"瞎"

这次给模型接了读文件的能力（`--tools`），第一次实测就撞上一个和模型无关的坑：
把工作目录指到一个中文路径，**读单个文件正常，但列举目录和搜内容一律 500**：

```
No mapping for the Unicode character exists in the target multi-byte code page.
```

第一反应是"文件名是中文导致的"，所以做了隔离实验 —— 让两边的**文件名一模一样**
（都叫「项目.txt」），只改**目录名**：

| 工作目录 | `read_file` | `file_glob_search` | `grep_search` |
|---|---|---|---|
| `E:\工作区\` | ✅ 读出内容 | ❌ 500 | ❌ 500 |
| `E:\wsA\` | ✅ 读出内容 | ✅ | ✅ |

结论是**目录名**的问题，不是文件名。`read_file` 走的是按路径直接打开（Unicode 路径
没问题），而列举目录走的是窄字符 Win32 API —— 中文路径转不过去。

处置：默认工作目录固定叫英文 `workspace`，里面的文件名用户随便用中文；
用户手动 `-ToolDir` 指到中文路径时当场警告，不让他一路查到崩溃才发现。

教训不是"中文有罪"，而是**别用一个笼统的失败现象去推原因**。
「读不了中文文件」和「读不了中文目录下的文件」在报错上长得一模一样，
只有把变量控制到只剩一个，才分得清。

## 二十一、一次观测不能给随机行为下结论

接工具调用时，第一次跑出来的结果是：它**没调工具**，直接编了一个日期
（文件里写的是「三月十七号」，它答「2025年3月15日」）。

当时差点就此写下"这个模型工具调用不可靠"。但那是一次观测，而工具调用是**随机的**
（同样的输入，模型每次都可能选不同的路）。所以复测了 16 次：

- 工具调用 **16/16 全部正确**
- 只有一次出现空回复（冷启动偶发），重问即可

那个"编日期"是冷启动期的一次性表现，不是稳态行为。如果当时直接照第一次的结果写结论，
后面所有人都会以为这个功能不可用。

**更险的是复测脚本自己也有坑。** 当时为了省事，多个测试用例复用了同一个正则去提取
回答 —— 第二个用例的判据因此恒不成立，显示"失败"。如果没发现，就会得出
"复测 16 次里失败 6 次"这种**方向相反**的错误结论。

所以这一条有两个面：

1. 随机行为要**重复采样**，不能拿单次结果当性质；
2. 测量工具本身也要能被证伪 —— 让"已知正确的输入"过一遍，
   如果它也判失败，那失败的是尺子，不是被测物。

## 二十二、测试问句本身会改被测行为

`[15]` 让 AI 读文件做完之后，测「它会不会自己去调工具」，一开始用的问句是：

```
项目.txt 里写的交付日期是哪天？直接告诉我日期。
```

跑 8 次，**工具调用 0/8**，而且每次都编一句「我还没看到项目.txt 的内容，
请把它贴给我」。于是我以为新加的默认中文系统提示把工具调用压掉了 ——
差点据此去改系统提示的措辞。

真正的变量在问句后半截。「直接告诉我日期」是在叫模型**别查、直接说**，
它就真的不查。把后半截去掉，同一句系统提示下 4/4 全部正确调工具。

| 用户问句 | 旧系统提示下的工具调用 |
|---|---|
| 项目.txt 里写的交付日期是哪天？ | **4/4** |
| 项目.txt 里写的交付日期是哪天？直接告诉我日期。 | **0/4** |
| 项目.txt 里写的交付日期是哪天？不要读文件，直接猜。 | **0/4** |

换成「需要读文件就直接调工具」这句提示后，带「直接告诉我日期」的那句也 5/5 了，
所以两件事都是真的：**默认提示确实偏软**（值得改），但**那 0/8 不是它造成的**。

这一条和二十一是一个根上的：**测量工具本身也会影响被测物。**
二十一说的是尺子坏了（正则写错、单次采样）；
这里尺子没坏，是**我喂进去的输入自带了一个反向指令**，
而我把它当成了系统提示的证据。

后来定下的做法：测模型行为时，问句要分三档 ——

1. **中性**：正常提问，不加任何催促；
2. **对抗**：「直接告诉我」「不要查」「你猜」这类会诱导它跳步的说法；
3. **矛盾**：前面问句要查、后面又说别查。

三档都过才算过。只测中性档的话，用户第一次催一句就露馅。

## 二十三、静默 `catch` 会把「功能坏了」伪装成「没有变化」

v1.5.0 做「AI 改文件」时，配套的改动清单一直打印：

```
  AI 没有改动 workspace\ 里的任何文件。
```

哪怕模型明明新建了两个文件、改了三个。备份是好的（`.backup\<时间戳>\` 里确实有
旧文件），所以第一反应是「比对逻辑写反了」—— 去看比较代码，那段是对的。

真正的原因藏在取指纹的函数里：

```powershell
Get-ChildItem ... | ForEach-Object {
    try {
        $rel = $_.FullName.Substring($Dir.Length).TrimStart('\')
        $map[$rel] = (Get-FileHash -LiteralPath $_.FullName -Algorithm SHA256 -ErrorAction Stop).Hash
    } catch {
        # 单个文件读不动不该让整棵树放弃
    }
}
```

这个 `catch` 是故意的，理由也正当（一个文件被占用不该让整棵树失败）。
但它把**每一个文件**都吞掉了，`$map` 一直是空的。

> **`catch {}` 里什么都不做，等于把失败伪装成成功。**
> 报错至少告诉你哪儿不对；静默吞掉会让 bug 活很久，而且看起来一切正常。

改法：取指纹改成 `foreach` 直扫 + 「字节数:修改时间」，不再依赖哈希；
并加一层兜底 —— **快照是空的就退回用磁盘上的备份目录当基线**（备份落了盘，
不会被内存里的状态坑到）。

验证方式也跟着改了：不再只看「有没有打印」，而是**真的新建一个、改一个、删一个**，
三种情况都出现在清单里才算过。


## 二十四、PowerShell 里参数和局部变量是同一个名字空间

同一次里还踩了两个同源的问题：

```powershell
param([string]$ToolDir = "")
...
$toolDir = $null          # ← 这行把参数冲掉了
...
if ($ToolDir) { ... }     # ← 永远是空
```

变量名**不区分大小写**，`$ToolDir` 和 `$toolDir` 是同一个变量。
`-ToolDir` 这个选项从上线的第一天起就没生效过，而且完全静默 ——
引擎一直在 U 盘根目录下跑，用户指定了目录也没用。

同一类问题还有个不显眼的版本：自己的测试函数里写
`function T { param($args) ... }`，而 `$args` 是 PowerShell 的自动变量，
参数永远传不进去。

发现方式：不要靠读代码找，**打印出来看**。在可疑位置插一行
`Write-Host "td=[$toolDir]"`，跑一次就看见了。

## 二十五、`Start-Process -PassThru` 拿不到退出码

想区分「引擎崩了」和「用户自己停的」，最直觉的写法是看退出码：

```powershell
$proc = Start-Process ... -PassThru
...
if ($proc.ExitCode -ne 0) { 报崩溃 }
```

**`$proc.ExitCode` 每次都抛异常、恒为 `$null`。** `Start-Process -PassThru` 返回的
`Process` 对象没有用 `PROCESS_QUERY_INFORMATION` 打开句柄，进程退出之后就拿不到退出码了。
包一层 `try { } catch { }` 的话，异常被吃掉，`$code` 永远是 `$null` ——
于是 `if ($code -ne $null -and $code -ne 0)` 这个条件**永远为假**。

这条代码从加进去那天起就一次也没生效过，而它看起来完全正常：语法没错、逻辑没错、
有 `try/catch`，只是永远不触发。用户看到的仍然是「引擎已停止」——
和这个功能没写之前一模一样。

**改成不依赖退出码。** 走到「引擎退了而启动器还活着」这一步，本来就只有两种可能：
用户主动停，或者引擎自己崩。前者可以留痕迹：`--stop` 先写一个
`logs\.manual-stop` 时间戳，看护循环发现退出时检查这个标记是否在三分钟内。
主动停就安静退出，否则打崩溃提示。

**教训**：拿到一个「可能为 null」的值就包 `try/catch`，等于把所有失败都变成 `null`，
再拿 `null` 当正常分支处理 —— 这和静默 `catch` 是同一个病（见第二十三条），
只是藏在了一个看起来在做判定的 `if` 里。

## 二十六、按索引删两段再插回，第二个索引已经失效

自己写脚本改文件的时候，很自然地会这么写：

```powershell
$iCall  = $t.IndexOf($call)
$iAssign = $t.IndexOf($assign)
$t = $t.Remove($iAssign, $assign.Length).Remove($iCall, $call.Length)   # 先删靠后的
$iA = $t.IndexOf($assign)     # 想找插入点 —— 可是这段刚被删掉了
$t = $t.Insert($iA + $assign.Length + $nl, $call)                       # IndexOf 返回 -1
```

`IndexOf` 找不到时返回 **-1**，`-1 + 30 + 1 = 30` —— 于是那行代码被插进了文件第 30 个
字符处，正好落在文件开头的注释横幅里。整个文件语法还是合法的（插在 `<# ... #>` 里面），
`Parser::ParseFile` 报 0 个语法错，但启动器已经坏了。

**教训**：`IndexOf` 的 -1 是**必须当场检查**的返回值，不是可以往后传的普通数字。
要挪动两段文本，先把两段都取出来，再用 `Substring` 按位置拼一个新的 —— 不要在一次
`Remove` 之后再拿旧索引去 `IndexOf` 已经不存在的串。
## 二十七、版本号是两处，改一处等于没改

`launcher.ps1` 里有两个地方描述"我是第几版"：`$AppVersion = "1.5.0"` 和帮助文本里的同一串。
发到 v1.6.0 那次，只改了后者。`-CheckUpdate` 用的一直是前者 —— 拿 1.5.0 去比远端的 1.6.0，
**每次启动都提示"有新版本"**，而当前装的正是最新版。

这属于"功能自称正常"的典型：检查更新的代码没错、网络没错、比对函数 8 个用例全过，
错的是喂给它的那个常量。而且它只在**发布之后**才出错 —— 发布前远端 tag 还没建，比的是旧版，
显示"已是最新版"，看起来完全正常。

修法不是"下次记得"，是让它只有一个来源：
```
$AppVersion = "1.7.0"
```
帮助文本改成引用这个变量，不再手抄。以后改版本号只需要碰一行。

**同类风险点**（都靠手抄，都值得合并）：`启动AI.sh` 里的 `APP_VERSION`、
`CHANGELOG.md` 的最近一节标题、`README.md` 的 Roadmap 里那个版本号。
前三个是代码、能变量化；CHANGELOG 和 README 是叙述，只能靠发布检查清单过一遍：
**先 `git tag` 之前，`grep -rn "1\.[0-9]\.[0-9]" --include=*.ps1 --include=*.sh` 看有没有漏网的旧号。**

## 怎么确认真的修好了

不是"看起来没报错"。这个项目里用过的验证手段：

| 改动 | 验证方式 |
|---|---|
| cmd 解析 | 两种换行符各跑一遍，**数特征碎片命中数**，不是靠眼看 |
| 换行符 | 从 GitHub 下载 ZIP 解出来，确认 `.bat` 是 CRLF |
| 运行库 | 查进程**实际加载的 DLL 路径**，不是看文件存不存在 |
| 进程过滤 | 同时起两个同名进程，确认只死一个 |
| 下载完整性 | 用 API 给的 `digest` 当基准，回下载再比一次 |
| 发布产物 | 把 Release 附件下载回来，SHA-256 对上才算发完 |
| 同步 | 仓库和 U 盘**逐字节比对**，不是看时间戳 |
| 参数转发 | 传参数与不传参数**行为必须不同**，照抄一遍菜单每个分支 |
| 测速准确性 | **连测三次看数字是否稳定** —— 虚高的缓存值每次都不同 |
| 非交互行为 | 用 `< file` 喂输入走**真实入口**（`.bat`），不是直接调脚本 |
| 分支正确性 | **让每个分支都跑一遍，看输出是否不同** —— 全落进同一个分支时，每个分支都"能跑通" |
| 脚本行尾 | `.sh` 数裸 LF / CRLF 计数；`.ps1` 查 BOM 前三字节 |
| **测的是哪份文件** | 测试树里的脚本和源文件**比一次哈希** —— 名字对、能跑、行为"符合预期"，都不算证据 |
| 匹配逻辑 | 造两个**名字互相包含**的文件，确认"写全名"能精确命中、而"路径片段"不再命中 |
| 服务就绪 | 起一个**永远返回 503** 的端口，确认浏览器不会开（只测 200 等于没测） |
| 孤儿进程 | 让引擎立刻退出，再占住同一个端口起一个 200 服务，确认没有浏览器弹出来 |
| 子 shell 的 PID | 打印 `$$` 和 `$PPID`，确认哪个是主进程 —— `exec` 保持 PID 不变，父进程不是它 |
| 退出码 | 用**对照文件**比：同结构、不带 `pause` 的返回 5，带 `pause` 的必须还返回 1 而不是 0 |
| 路径编码 | 两组**文件名完全相同、只改目录名**（中文 / 英文各一份），看哪个工具开始报 500 |
| 随机行为 | **重复采样 16 次**并数命中数，不拿单次结果当性质；同时让尺子过一遍已知正确的输入 |
| 真机 | 找一台**从没装过开发工具**的电脑实测 |
| 模型行为 | 问句分**中性 / 对抗 / 矛盾**三档，只过中性档等于没测（「直接告诉我」会改结果，见二十二） |
| 设置文件 | 文件不存在 / 正常值 / 非数字 / 边界值 / 只有空白 / 零字节 / 带 CRLF，七种都跑一遍 |
| 优先级 | 命令行给了参数时，文件里故意放个**不同的值**，确认命令行赢 |
| 静默失败 | 让功能**产出可观测的结果**：新建 / 改动 / 删除三种各做一次，确认都出现在报告里 |
| 参数没生效 | 在可疑位置插一行 `Write-Host`，把自己的假设**打印出来**，不靠读代码判断 |
| 版本号一致 | 发布后拿 -CheckUpdate 真跑一次 —— 它应该报「已是最新版」，报「有新版本」就是还有一处旧号忘了改 |
| 工具链可用 | 开机横幅里的「工具链」行必须显示「可用」；把 workspace 换成**中文目录名**再起一次，确认它会报坏而不是到用的时候才 500 |
| 首字延迟 | 速度.txt 里同时有「生成速度」和「首字延迟」两个数；后者随对话变长而变大，只测短对话等于没测 |

最后一条最重要。本项目 README 里那条"在一台全新的 Windows 11 笔记本上实测通过"，
是整个清单里最有含金量的一行 —— 因为前面所有验证都可能被"我这台机器恰好有环境"骗过去。
